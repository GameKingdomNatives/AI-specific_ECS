# ADR-030 运行时所有权：作者节点、spawner 实体与玩家语义

- 状态：已接受（D0）
- 日期：2026-10-22
- 相关：ADR-024/029、`docs/audits/数据驱动运行时计划.md`

## 背景

S5b 让 scene 驱动运行时后，暴露出三个数据驱动语义问题：

1. **玩家删除不生效**：`resolvePlayer` 在 scene 缺少 player 时按旧路径补建，删掉 player 节点看起来「没删」。
2. **节点与实体并非全部 1:1**：作者节点确实 1:1（S1 的 `entities` map），但 64 个 ambient 箱子由 `spawnSpec` 代码生成，没有对应节点，目标节点也没有角色语义。
3. **编辑同步**：保存通过 Vite watcher 触发整页 reload，编辑器状态丢失；玩家/系统引用在启动时固定。

## 决策

1. **两类所有权**：
   - **作者节点（authored）**：scene.nodes 中的每个节点 1:1 实例化为实体，映射存 `LoadedScene.entities` / `__itbScene.entities`。
   - **spawner 实体（spawned）**：由场景里的 spawner 组件在运行时生成（D2 实现），归属 spawner 节点，不进入节点映射；运行时快照记录 `nodeId → 生成数量`。
   - 编辑器对两类分别显示：节点显示 `E<id>`，spawner 节点显示「生成 N」。
2. **玩家语义**：scene 成功加载时，player 节点存在就用它；**缺失时不再静默补建**。玩家相关系统以 `-1` 哨兵安全跳过（`world.get(-1)` 为 undefined），HUD 显示 `player missing`。只有 scene 整体不可用（降级路径）才补建玩家，保证旧路径可玩。
3. **运行时快照**：`__itbScene = {name,nodes,systems,issues,entities: Record<nodeId,entityId>, player: entityId|null, spawned: Record<nodeId,count>}`，供编辑器/调试读取。
4. **同步策略**：D1 先做到「保存 → 已知会 reload → 运行时重建」，并把节点/实体映射暴露给编辑器；D3 再实现保留编辑器状态的原地重建（ADR-031）。
5. **AI 质量护栏**：每个阶段都必须有 schema/单测或浏览器证据 + 全量门禁；不得用 `any`/断言绕过；端口契约保持不变；文档与代码同一提交。

## 验收（D1）

- 删除 player 节点并保存 → 页面重载后 `__itbScene.player=null`、HUD `player missing`、实体数为 66（64 ambient + root + target），玩家不再出现。
- 编辑器场景树显示 `player E<id>` 等映射；`__itbScene.entities` 可读。
- 恢复 player 节点 → 玩家恢复，`__itbScene.player` 为有效实体。
- 全量门禁 PASS。

## 后果

- 正面：删除就是删除；作者节点与运行时实体关系可见；为 spawner 与实时重建铺路。
- 代价：删除玩家后游戏进入无玩家状态（当前没有「必需节点」声明）；D2 会加节点角色/必需标记与编辑器提示。
- 回退：`resolvePlayer` 的旧行为只在 scene 不可用时保留。
