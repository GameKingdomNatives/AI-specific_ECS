# ADR-025 调度数据化（scene 系统清单 → Scheduler）

- 状态：已接受（S2）
- 日期：2026-10-22
- 相关：`docs/audits/场景编辑器计划.md` S2、ADR-024

## 背景

现有调度顺序在 `apps/game/src/system-registry.ts` 用代码数组写死；scene JSON 已有 `systems` 清单（id/phase/enabled/after/params），但还没有把它接到 `Scheduler`。编辑器要能调整阶段、顺序与启用状态，必须先有稳定的「清单→调度器」构造层。

## 决策

1. **构造层**：`scene/schedule.ts::buildSchedule(scene, build)`，`build: (id, params, phase) => SystemDef | undefined` 由应用注册表提供；引擎不依赖具体系统。
2. **phase 以 scene 为准**：工厂返回的 SystemDef 复制一份并覆盖 `phase`，让编辑器可以移动系统阶段；系统内部若依赖阶段语义，由注册表在工厂里保证。
3. **after 合并**：最终 `after = 系统自带 after ∪ scene after`（去重）；`before` 保留系统自带。顺序冲突仍由 `Scheduler` 的拓扑/冲突校验兜底。
4. **enabled=false**：不加入调度器，但保留在 `disabled` 列表供编辑器显示；不会调用工厂。
5. **params 透传**：scene 只允许标量参数（number/string/boolean），工厂自行校验/消费；引擎不做系统私有 schema（S2 范围）。
6. **错误语义**：未注册 id、工厂 name 与清单 id 不一致、scene 内 after 环都进 `issues`，不抛异常；环存在时不返回任何系统，避免半套调度。
7. **双轨**：S2 只交付引擎构造层；现有 `main.ts/system-registry.ts` 保持代码路径，S5 再接应用默认关卡。

## 验收

- 单测：phase 覆盖、after 合并、disabled 跳过且不调用工厂、params 透传、未注册/改名 issue、after 环、构造结果可被 `Scheduler` 直接执行。
- 全量门禁 PASS。

## 后果

- 正面：调度顺序/阶段/启用成为场景数据；编辑器保存即可改变运行顺序。
- 代价：phase 覆盖可能与系统内部假设冲突，需要注册表约束；`params` 暂无统一 schema，S3/S4 的编辑器表单需要按系统声明字段（后续补）。
- 回退：代码注册表路径不变，`buildSchedule` 不启用时零影响。
