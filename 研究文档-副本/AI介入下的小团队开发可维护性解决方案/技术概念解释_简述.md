# 上述架构中引入的技术概念简解

---

## 一、IDL（Interface Definition Language，接口定义语言）

**是什么**：一种中立的、与编程语言无关的格式，用来描述接口、数据结构、通信协议。

**解决什么问题**：不同模块可能用不同语言写（C++ 热系统、C# 工具、Lua 脚本），IDL 是它们之间的“共同语言”。改 IDL，自动生成各语言的桩代码。

**常见 IDL**：
| IDL | 典型场景 | 特点 |
|-----|---------|------|
| Protobuf | 网络通信、存档 | 二进制高效，生态成熟 |
| FlatBuffers | 游戏热路径 | 零拷贝读取，适合每帧访问 |
| Thrift | 企业 RPC | 支持多种传输协议 |
| TypeScript interface | 前端/工具链 | 轻量，无需代码生成 |
| Rust trait | Rust 模块间 | 编译期检查，零运行时开销 |

**简单示例**：
```protobuf
// combat.proto
message DamageEvent {
  uint32 target_id = 1;
  float amount = 2;
  DamageType type = 3;
}
```
构建系统自动生成 C++ 的 `DamageEvent` 类、C# 的类、Lua 的表结构。AI 只读 `.proto`，不读生成代码。

## 二、DI（Dependency Injection，依赖注入）

**是什么**：模块不自己创建依赖，而是从外部“注入”进来。

**解决什么问题**：模块 A 需要数据库，但不该知道数据库是 MySQL 还是 SQLite。DI 让具体实现在运行时决定。

**简单示例**：
```cpp
// 不好：自己创建，编译期耦合
class QuestSystem {
    MySQLDatabase db;  // 换数据库要改代码
};

// 好：注入接口
class QuestSystem {
    IDataStore& store;  // 只依赖抽象
public:
    QuestSystem(IDataStore& s) : store(s) {}  // 由外部注入
};

// 运行时决定
MySQLDatabase mysql;
QuestSystem quest(mysql);  // 生产环境

MockDatabase mock;
QuestSystem test(mock);    // 测试环境
```

**变体**：
- **构造函数注入**：通过构造参数传入（最常用）。
- **服务定位器**：模块主动从全局容器拉取（灵活但隐藏依赖）。
- **DI 容器**：自动解析依赖图，适合复杂项目。

## 三、SoA（Structure of Arrays，数组结构）

**是什么**：把“每个对象存所有属性”改成“每个属性存一个数组”。

**解决什么问题**：CPU 缓存友好。遍历 10000 个粒子时，SoA 只加载位置数组，不加载无关数据。

**对比 AoS（Array of Structures）**：
```
// AoS：每个粒子存所有属性，遍历位置时缓存被无用数据污染
struct Particle { Vec3 pos; Vec3 vel; Color color; float life; };
Particle particles[10000];

// SoA：按属性拆数组，遍历位置时只加载位置
struct Particles {
    Vec3 pos[10000];    // 连续内存，缓存命中率高
    Vec3 vel[10000];
    Color color[10000];
    float life[10000];
};
```

**在 ECS 中的应用**：每个 Component 类型就是一个数组，System 通过 Query 访问。物理系统只读 `pos` 和 `vel`，渲染系统只读 `pos` 和 `mesh`，各自缓存友好。

## 四、事件总线（Event Bus）

**是什么**：一个中央枢纽，发布者发事件，订阅者收事件，双方互不知道对方存在。

**解决什么问题**：跨模块通信不产生直接依赖。战斗系统发 `DamageEvent`，不知道有成就、音频、UI 在监听。

**简单示例**：
```cpp
// 发布者
bus.publish(DamageEvent{target, 25.0f});

// 订阅者
bus.subscribe<DamageEvent>([](const DamageEvent& e) {
    achievementSystem.check(e);
});
```

**同步 vs 异步**：
- **同步**：发布后立即调用所有订阅者，帧内响应，但阻塞发布者。
- **异步队列**：事件入队，帧末统一处理，不阻塞，但延迟一帧。

## 五、命令缓冲（Command Buffer）

**是什么**：不直接修改状态，而是把“修改意图”记录到缓冲区，帧末统一执行。

**解决什么问题**：遍历过程中修改集合会导致迭代器失效；多个系统修改同一状态导致顺序依赖。

**简单示例**：
```cpp
// 不直接 destroy，而是记录意图
cmdBuffer.destroyEntity(enemyId);
cmdBuffer.spawnEntity(bulletPrefab, pos);

// 帧末统一执行，顺序可控
cmdBuffer.flush(world);
```

**收益**：系统之间不需要知道彼此的修改顺序；支持撤销/重做；支持录制回放调试。

## 六、能力注册表（Capability Registry）

**是什么**：一张中央清单，记录系统提供哪些能力、契约、版本、拥有者。

**解决什么问题**：AI 生成代码前先查表，避免重复实现已有功能；人类快速了解系统全貌。

**简单示例**：
```yaml
- name: combat.damage
  contract: contracts/combat.proto#DamageEvent
  provider: CombatModule
  version: 2.1.0
  owner: team-combat
  performance: "< 0.1ms per call"
```

**工作流**：AI 要实现“造成伤害”，先查注册表 → 发现已有能力 → 复用契约，不重新实现。

---

## 七、契约测试（Contract Test）

**是什么**：验证实现是否满足接口语义的测试。测试由人类编写或审批，AI 不能改。

**解决什么问题**：AI 生成的实现可能“语法正确但语义错误”。契约测试是执法机制。

**简单示例**：
```cpp
TEST(DamageContract, AppliesCorrectAmount) {
    ICombatSystem& combat = createCombatSystem();
    combat.applyDamage(target, 25.0f);
    EXPECT_EQ(combat.getHealth(target), 75.0f);  // 契约规定：伤害直接扣血
}
```

**与单元测试的区别**：单元测试测实现细节，契约测试测接口语义。契约测试跨实现版本稳定。

---

## 八、架构约束测试（Architecture Fitness Test）

**是什么**：自动检查代码是否符合架构规则的测试。

**解决什么问题**：AI 可能“不小心”跨模块直接引用、热路径用了事件总线。人工审查不可靠，自动检查可靠。

**简单示例**：
```python
def test_no_cross_module_reference():
    """检查模块间无直接 include"""
    for module in modules:
        for dep in module.includes:
            assert dep in module.allowed_deps, f"{module} 非法引用 {dep}"

def test_hot_path_no_event_bus():
    """检查热路径代码不调用事件总线"""
    for file in hot_path_files:
        assert "eventBus.publish" not in file.content
```

**在 CI 中**：架构测试失败 = 阻止合并，无论功能测试是否通过。

## 九、热重载（Hot Reload）

**是什么**：不重启程序，替换模块的动态库，保留状态。

**解决什么问题**：游戏启动慢，改一行代码重启要几分钟。热重载让迭代从分钟级降到秒级。

**简单示例**：
```cpp
// 监听动态库变化
hotReloader.watch("WeaponSystem.dll", [&]() {
    scheduler.replaceSystem<WeaponSystem>(loadDll("WeaponSystem.dll"));
});
```

**前提**：模块无全局状态、通过组件/事件通信。这反过来强迫解耦。

## 十、沙箱 VM（Sandbox Virtual Machine）

**是什么**：第三方代码运行在受限环境中，只能访问暴露的 API，不能碰引擎内部。

**解决什么问题**：Mod/脚本崩溃不影响引擎；恶意代码不能破坏系统。

**常见沙箱**：
| 技术 | 特点 |
|------|------|
| Lua | 轻量，游戏 Mod 常用 |
| WASM | 性能好，语言无关，浏览器/引擎通用 |
| C# AppDomain | .NET 生态，Unity 常用 |
| JavaScript (V8) | 生态丰富，工具链成熟 |

**简单示例**：
```lua
-- Mod 只能调用暴露的 API
game.spawnEntity("bullet", {x=10, y=20})
game.onEvent("playerDied", function(e) ... end)
-- 不能访问引擎内存、不能调用系统 API
```

## 十一、Spec（Specification，规范）

**是什么**：功能的权威描述，包含类型签名、行为语义、测试用例。是人类和 AI 的共同语言。

**解决什么问题**：AI 直接写代码容易偏离意图。先写 Spec，人类审批，AI 按 Spec 实现。

**简单示例**：
```markdown
## 能力：伤害计算

输入：DamageEvent { target, amount, type }
输出：HealthChangedEvent { target, newHealth }
语义：
- 伤害直接扣血，不考虑护甲
- 血量最低为 0，触发 DeathEvent
- 同一帧多次伤害累加
测试：
- 100 血受 25 伤 → 75 血
- 10 血受 25 伤 → 0 血 + DeathEvent
```

**工作流**：Spec 是人类审批的对象，代码是实现细节。Spec 变更走 HARD gate。

---

## 十二、影响分析（Impact Analysis）

**是什么**：自动计算一个代码变更影响哪些模块。

**解决什么问题**：AI 改一个接口，可能破坏 10 个下游模块。影响分析让审查者快速判断风险。

**简单示例**：
```
变更：combat.proto 的 DamageEvent 删除 type 字段
影响：
  - CombatModule（直接修改）
  - AchievementModule（消费 DamageEvent）
  - UIModule（消费 DamageEvent）
  - ReplayModule（录制 DamageEvent）
影响范围：4 个模块 → 自动升级为 HARD gate
```

## 概念关系图

```
Spec（规范）
  │ 驱动
  ▼
IDL（契约）──→ 代码生成 ──→ 各语言桩代码
  │
  │ 实现
  ▼
模块 ──→ DI（注入依赖）──→ 接口隔离
  │
  │ 通信
  ▼
事件总线 / 命令缓冲 ──→ 解耦
  │
  │ 数据
  ▼
SoA（热路径）/ 引用（冷路径）
  │
  │ 治理
  ▼
能力注册表 · 契约测试 · 架构约束测试 · 影响分析
  │
  │ 运行时
  ▼
热重载 · 沙箱 VM · 崩溃隔离
```
