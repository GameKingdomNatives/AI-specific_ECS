# 自举：先建一个“不完美但能执法”的框架，再长出完全合规的系统

你问的这个问题，本质上就是**编译器自举**和**操作系统自举**的同构问题：能不能先用一个粗糙的工具，造出更好的工具，再用更好的工具造出最终产品？答案是**能，而且这可能是小团队唯一现实可行的路径**。但“从零开始开发高度符合规范的版本”则几乎不可能——原因和为什么不能一次性写出完美编译器一样。

---

## 一、自举的核心原理

### 原理：执法者先于守法者存在

任何规范体系要运转，必须先有一个**执法机制**。但执法机制本身也需要被规范约束。这就产生了鸡生蛋问题。

解决方案是**分层递推**：

```
第 0 层：人工执法（最粗糙，但绝对可靠）
   ↓ 用人工执法构建
第 1 层：半自动执法器（脚本 + CI，覆盖核心规则）
   ↓ 用半自动执法器构建
第 2 层：自动执法器（架构测试 + 契约检查 + 权限 gate）
   ↓ 用自动执法器构建
第 3 层：完全合规的系统（AI 在完整约束下自主生成）
```

每一层的执法器**不需要完美**，只需要**能覆盖当前层已知的规则**。然后用它去构建下一层，下一层再覆盖更多规则。这是**增量收敛**，不是一次性到位。

### 类比：Rust 编译器的自举

Rust 编译器最初用 OCaml 写，然后用 Rust 重写自己。第一版 Rust 编译器并不完全符合 Rust 的所有规则——它只是**足够好，能编译出更好的编译器**。经过多轮迭代，最终编译器才完全符合规范。

游戏框架的自举同理：第一版框架可能只强制了“模块间不能直接 include”这一条规则，但它足以支撑开发出第二版框架，第二版再强制“事件 Schema 必须版本化”，以此类推。

## 二、分阶段自举路线图

### 阶段 0：人工执法 + 约定（1-2 周）

**目标**：建立最小可用的规范共识，不写任何自动化工具。

**具体事项**：
- 团队开半天会，确定 3-5 条**不可妥协**的核心规则。例如：跨模块通信只能走事件总线；每个模块必须有 `module.toml` 声明所有权；热路径禁止事件总线。
- 规则写在 `CONTRIBUTING.md` 中，代码 Review 时人工检查。
- 建立模块清单文件的**手工模板**，每个模块复制粘贴填写。
- 事件总线用现成组件接入，事件 Schema 先写在代码注释里。

**为什么这步不能跳过**：如果连人工执法都做不到，自动化执法只会让团队绕过它。先让团队**习惯规则存在**，再自动化。

**执法器能力**：0%。完全靠人。

---

### 阶段 1：脚本执法器（2-4 周）

**目标**：把能自动化的规则用脚本覆盖，减少人工 Review 负担。

**具体事项**：
- 写一个 `check_module_boundaries.py`：解析 `module.toml`，检查代码中是否有跨模块直接 include。有则 CI 失败。
- 写一个 `check_hot_path.py`：扫描热路径目录，检查是否有事件总线调用、序列化、虚函数。有则警告。
- 写一个 `check_contract_version.py`：对比 IDL 文件的 Git 历史，检测破坏性变更，标记为 HARD gate。
- 事件 Schema 从注释迁移到独立的 `.proto` 或 `.ts` 文件，脚本检查 Schema 是否被实现引用。
- 建立能力注册表的**手工维护 CSV 文件**，脚本检查新增模块是否在注册表中登记。

**执法器能力**：覆盖核心规则的 30-50%。剩下靠人工。

**关键决策**：这个阶段的执法器**本身不需要符合规范**。它就是一堆 Python 脚本，放在 `tools/` 目录下，不属于任何游戏模块。这是自举的关键——**执法器是元层，不受被执法层的规范约束**。

---

### 阶段 2：架构测试 + CI Gate（1-2 月）

**目标**：把脚本升级为正式的架构测试套件，集成到 CI 中，实现自动分类和权限 gate。

**具体事项**：
- 把 Python 脚本重写为**测试框架内的架构测试**（如 pytest、GTest、Rust 的 `#[test]`），与单元测试一起运行。
- 建立**影响范围分析器**：解析模块依赖图，计算一个 PR 的影响范围，自动分类为 AUTO / SOFT / HARD。
- CI 配置：AUTO 通过即合并，SOFT 异步审查，HARD 阻止合并。
- 契约测试从“手写几个用例”升级为**从 IDL 自动生成测试骨架**，人类填充语义断言。
- 能力注册表从 CSV 迁移到**结构化数据文件**（YAML/JSON），脚本自动生成文档和依赖图。
- 热重载基础设施接入，模块独立编译为动态库。

**执法器能力**：覆盖核心规则的 70-80%。人工只处理 HARD gate 和契约语义审查。

**自举的关键跃迁**：这个阶段的架构测试**本身是用阶段 1 的脚本执法器构建的**。阶段 1 的脚本检查了架构测试代码的模块边界，确保架构测试不违反被执法层的规则。这是第一次“用执法器构建执法器”。

---

### 阶段 3：Spec 驱动 + AI 自主生成（持续）

**目标**：Spec 成为权威来源，AI 在完整约束下自主生成实现，人类只审批 Spec 和契约变更。

**具体事项**：
- 建立 **Spec 仓库**：每个功能先写 Spec（自然语言 + 类型签名 + 测试用例），Spec 走 HARD gate。
- AI 读取 Spec + 契约 + 能力注册表，生成实现代码和单元测试。
- CI 运行架构测试 + 契约测试 + Spec 测试，全部通过则 AUTO 合并。
- 人类只审查：Spec 变更、契约变更、HARD gate PR、架构测试本身的变更。
- 架构测试套件从“手写检查”升级为**从 Spec 和契约自动生成检查**——Spec 定义了什么，架构测试就检查什么。
- 能力注册表从 YAML 迁移到**可查询的服务**，AI 在实现前先查询注册表，避免重复实现。

**执法器能力**：覆盖核心规则的 90%+。人类只处理语义冲突和架构演进决策。

**自举完成**：这个阶段的架构测试**是用阶段 2 的架构测试构建的**。阶段 2 的测试检查了阶段 3 测试代码的合规性。最终，系统完全合规，因为**合规性是由系统自身定义的测试强制执行的**。

## 三、为什么“从零开始开发高度符合规范的版本”不可能

### 原因一：规范是在开发中发现的，不是预先设计的

没有人能在第一天就知道“热路径禁止事件总线”这条规则。它是在开发中发现“事件总线在物理系统里造成了 5ms 开销”之后才被总结出来的。**规范是经验的压缩，不是先验的真理。**

试图从零开始写一个完全符合规范的版本，等于要求团队在没有任何开发经验的情况下设计出完美规范。结果只有两种：要么规范过于宽松（没约束力），要么规范过于严苛（无法落地）。

### 原因二：执法器本身需要被开发，而开发需要时间

即使团队预知了所有规范，执法器的开发也需要时间。在执法器完成之前，代码已经在增长。如果等到执法器完全就绪再开始写游戏代码，团队会在等待中饿死。

自举的意义在于：**允许执法器和被执法代码同步演进**。执法器先覆盖最重要的规则，游戏代码先跑起来，然后逐步收紧约束。

### 原因三：AI 辅助放大了“先写后补”的成本

AI 生成代码的速度远快于人类审查速度。如果规范不成熟就大量生成代码，技术债会以 AI 的速度积累。但这不意味着要等规范完美——而是意味着**规范的第一条必须是“禁止在无契约的情况下生成跨模块代码”**。用最低限度的规范约束 AI，然后用 AI 生成的代码验证规范，再收紧规范。

## 四、自举的实践模式

### 模式一：执法器元层不受约束

```
┌─────────────────────────────────────┐
│  元层：执法器（脚本、测试、CI）        │  ← 不受被执法层规范约束
│  可以用 Python 快速写，可以硬编码      │
├─────────────────────────────────────┤
│  被执法层：游戏模块                   │  ← 受完整规范约束
│  必须走事件总线、必须声明所有权        │
└─────────────────────────────────────┘
```

元层用最粗糙的方式实现，只要**能执法**即可。元层自身的代码质量、架构合规性可以放宽。这是自举能启动的关键。

### 模式二：规范以“禁止”为主，而非“要求”

早期规范应该只写**禁止项**，不写推荐项：

- 禁止：跨模块直接 include
- 禁止：热路径调用事件总线
- 禁止：无契约的跨模块调用

不要写：“建议使用依赖注入”、“推荐用 SoA 布局”。因为禁止项可以用脚本强制检查，推荐项无法自动化。等禁止项被完全执法后，再逐步加入推荐项。

### 模式三：每层只增加一条规则

不要一次性加入 10 条规则。每层自举只增加**1-2 条可自动检查的规则**。加完规则后，让团队和 AI 在新约束下运行一段时间，验证规则不会造成过多摩擦，再增加下一条。

### 模式四：契约测试是自举的种子

契约测试是唯一一个**从第一天就必须存在**的规范。因为契约测试是 AI 生成代码的裁判。如果第一天没有契约测试，AI 生成的代码就没有裁判，技术债会失控。

契约测试本身可以很简单：一个函数，输入固定，输出断言。不需要框架，不需要 CI，先放在代码里，人工运行。然后用这个契约测试去构建更好的契约测试基础设施。

## 五、代价评估：小团队是否扛得住

### 可接受的代价

- **阶段 0-1**：1-2 人月。主要是写脚本和调整团队习惯。这个代价极低，几乎任何团队都扛得住。
- **阶段 2**：2-4 人月。架构测试、影响分析、CI gate 的开发。需要 1 名有 CI/DevOps 经验的成员投入。
- **阶段 3**：持续投入，每月 0.5 人月维护 Spec 和架构测试。

总计：**前 6 个月额外投入约 4-6 人月**，之后每月 0.5 人月维护。对于 5-10 人小团队，这意味着前期效率降低 20-30%，6 个月后效率提升 50%+（AI 自主生成 + 自动审查）。

### 不可接受的代价

- **试图跳过阶段 0-1**：直接上完整架构测试和权限 gate。结果：团队被复杂工具淹没，规则无法落地。
- **试图从零写完美规范**：在没有任何开发经验的情况下设计完整规范。结果：规范脱离实际，被绕过。
- **执法器元层也追求合规**：用事件总线和 DI 容器写架构测试脚本。结果：执法器比被执法代码还复杂，自举无法启动。

---

## 六、最终回答

**可以自举。** 先建一个粗糙但能执法的框架（阶段 0-1），用它构建更好的执法器（阶段 2），再用更好的执法器构建完全合规的系统（阶段 3）。这是编译器自举、OS 自举的同构问题，有成熟的理论和实践支撑。

**不能从零开始开发高度符合规范的版本。** 因为规范是在开发中发现的，执法器需要时间开发，AI 放大了无约束生成的风险。试图一步到位等于要求团队在真空中设计完美规范，必然失败。

**小团队扛得住。** 前期投入 4-6 人月，之后每月 0.5 人月维护，换来的是 AI 生成代码的安全可控、团队并行开发的解耦、以及长期维护成本的降低。代价可接受，但前提是**分层递推，不跳步**。

**核心心法：执法者先于守法者存在，元层不受被执法层约束，规范以禁止为主，每层只加一条规则，契约测试是自举的种子。**
