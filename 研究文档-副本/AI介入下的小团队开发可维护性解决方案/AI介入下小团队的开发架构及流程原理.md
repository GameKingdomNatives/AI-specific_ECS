# AI 介入下小团队的技术实现架构：从原理到落地

下面按“原理 → 要点 → 具体事项”三层展开。原理是为什么这样设计，要点是架构必须满足的约束，具体事项是团队实际要搭建或执行的动作。

---

## 原理一：契约主权

**核心思想**：接口契约是系统中唯一的公共表面。所有跨模块交互必须通过契约，实现代码是私有的、可替换的、AI 可自由生成的。

### 要点 1.1：契约必须用机器可读的 IDL 定义

**具体事项**：
- 选定一种 IDL（Protobuf、TypeScript interface、Rust trait、FlatBuffers 均可），全项目统一。
- 每个模块的契约文件独立存放，如 `contracts/combat.proto`。
- 契约文件纳入版本控制，变更走独立的 PR 流程。
- 构建系统从 IDL 自动生成各语言的桩代码，禁止手写跨模块调用。

### 要点 1.2：契约变更需要人类审批，实现变更 AI 自主

**具体事项**：
- CI 中增加契约兼容性检查：破坏性变更（删字段、改类型、改语义）自动标记为 HARD gate，必须人类审批。
- 非破坏性变更（加字段、加可选方法）标记为 SOFT gate，异步审查。
- 实现代码变更标记为 AUTO gate，AI 可自主提交，测试通过即合并。
- 建立契约版本号规则：主版本号变更 = 破坏性，次版本号 = 增量。

### 要点 1.3：契约测试是执法机制

**具体事项**：
- 每个契约配一套契约测试，验证实现是否满足接口语义。
- 契约测试由人类编写或审批，AI 不能修改测试本身。
- CI 中契约测试失败 = 阻止合并，无论实现代码看起来多正确。
- 契约测试覆盖：正常路径、边界条件、错误处理、幂等性。

## 原理二：数据所有权分离

**核心思想**：每个模块只读写自己声明的数据。跨模块数据访问只能通过查询或事件，禁止共享可变状态。

### 要点 2.1：每个模块显式声明其拥有的数据类型

**具体事项**：
- 建立模块清单文件（如 `module.toml`），声明 `owned_types`、`read_types`、`emitted_events`、`consumed_events`。
- 构建系统检查：如果模块 A 写了模块 B 拥有的类型，编译失败。
- 跨模块只读访问通过查询接口，不直接暴露内部数据结构。
- 禁止全局可变单例，所有状态归属明确模块。

### 要点 2.2：热路径用数据导向布局，冷路径用引用隔离

**具体事项**：
- 热系统（渲染、物理、动画）的数据按 SoA（Structure of Arrays）布局，System 通过 Query 访问。
- 冷系统（任务、成就、UI）的数据可以是指针/引用，但只能通过接口访问。
- 建立性能预算表：每个热系统的每帧耗时上限，超出则架构测试失败。
- 热路径禁止事件总线、禁止序列化、禁止虚函数调用。

### 要点 2.3：命令缓冲消除时序耦合

**具体事项**：
- 实现一个帧内命令缓冲：所有状态变更以命令对象形式入队，帧末统一执行。
- 命令类型：Spawn、Destroy、SetComponent、EmitEvent。
- 系统之间不直接修改彼此状态，只发命令。
- 命令缓冲支持撤销/重做，用于调试和回放。

## 原理三：通信路径收敛

**核心思想**：跨模块通信只有一种方式。路径收敛让 AI 生成的代码可预测，让审查者能快速判断合规性。

### 要点 3.1：进程内事件总线是唯一的跨模块通信机制

**具体事项**：
- 实现一个类型安全的发布/订阅总线，事件定义为纯数据（无行为）。
- 同步事件用于帧内需立即响应的场景，异步队列事件用于可延迟逻辑。
- 事件总线支持录制/回放，用于调试和回归测试。
- 禁止模块间直接函数调用（编译期检查：跨模块 include 触发警告或错误）。

### 要点 3.2：事件命名和版本化规则

**具体事项**：
- 事件命名：`<模块>.<动作>`，如 `combat.DamageApplied`、`quest.QuestCompleted`。
- 每个事件有 schema 定义，字段只增不减，旧字段标记 deprecated。
- 事件订阅者声明其消费的事件类型和版本范围。
- 事件发布者不知道订阅者存在，订阅者不知道发布者存在。

### 要点 3.3：依赖注入隔离具体实现

**具体事项**：
- 模块间依赖通过接口注入，不在编译期绑定具体类型。
- 建立服务定位器或 DI 容器，运行时决定注入什么实现。
- 平台相关代码（Steam、主机、云存档）封装在接口后，通过 DI 切换。
- 测试时注入 Mock 实现，不需要启动整个游戏。

## 原理四：权限分层

**核心思想**：按影响范围分层 AI 权限。影响越大，人类审批越严格。小团队用自动化 gate 替代人工审查。

### 要点 4.1：定义 AUTO / SOFT / HARD 三层权限

**具体事项**：
- **AUTO**：模块内部实现、纯重构、单元测试、文档。AI 自主提交，CI 通过即合并。
- **SOFT**：新增模块边界、增量契约变更、新事件定义。AI 提交，人类异步审查（24h 内）。
- **HARD**：修改根契约、破坏性接口变更、热路径核心代码、安全相关。必须人类审批，AI 只能提议。
- 权限规则写入 CI 配置，自动分类每个 PR。

### 要点 4.2：影响范围分析自动化

**具体事项**：
- 建立模块依赖图，CI 自动计算一个变更的影响范围。
- 影响范围 = 直接修改的模块 + 所有下游依赖者。
- 影响范围超过阈值（如 3 个模块）自动升级为 HARD gate。
- 影响范围报告附在 PR 中，帮助审查者快速判断。

### 要点 4.3：回滚和熔断机制

**具体事项**：
- 每个模块独立编译为动态库，支持热重载和独立回滚。
- 模块崩溃时，运行时自动重启该模块，不影响其他模块。
- 建立熔断规则：某模块连续失败 N 次，自动降级为安全模式。
- 所有 AUTO 合并的变更可一键回滚，回滚不需要人类审批。

## 原理五：Spec 作为真相

**核心思想**：规范是权威来源，代码是实现。AI 在实现前查询能力注册表，避免重复生成功能重叠的代码。

### 要点 5.1：能力注册表是系统能力的权威地图

**具体事项**：
- 建立中央注册表，记录每个模块提供的能力、契约、版本、拥有者。
- 注册表条目包含：能力名称、输入/输出契约、依赖、性能特征。
- AI 在实现新功能前，先查询注册表：如果已有能力，复用契约；如果没有，提议新增。
- 注册表变更触发下游影响分析。

### 要点 5.2：Spec 驱动代码生成

**具体事项**：
- 每个功能先写 Spec（可以用自然语言 + 类型签名 + 测试用例）。
- Spec 是人类和 AI 的共同语言：人类审批 Spec，AI 生成实现。
- Spec 纳入版本控制，与代码同仓库，变更走 HARD gate。
- CI 验证实现是否符合 Spec：Spec 中的测试用例必须全部通过。

### 要点 5.3：架构约束测试自动拦截违规

**具体事项**：
- 编写架构测试：检查模块间无直接引用、热路径无事件总线、契约变更合规。
- 架构测试在 CI 中运行，失败 = 阻止合并。
- 架构测试由人类维护，AI 不能修改。
- 违规报告附修复建议，AI 可根据报告自动修复。

---

## 原理六：故障隔离

**核心思想**：一个模块的崩溃不影响其他模块。模块可独立编译、测试、热重载。

### 要点 6.1：模块是独立编译单元

**具体事项**：
- 每个模块独立编译为动态库（.dll / .so / .dylib）。
- 模块间通过契约通信，不通过静态链接。
- 构建系统支持增量编译：只重编修改的模块。
- 模块有独立测试套件，可单独运行。

### 要点 6.2：热重载基础设施

**具体事项**：
- 运行时支持替换模块动态库，不重启游戏。
- 热重载时，模块状态通过序列化/反序列化保留。
- 热重载失败自动回滚到上一版本。
- 热重载用于开发迭代：修改武器逻辑，3 秒内看到效果。

### 要点 6.3：沙箱化脚本 / 插件运行时

**具体事项**：
- 第三方代码（Mod、脚本）运行在沙箱 VM（Lua、WASM、C# AppDomain）中。
- 沙箱只暴露稳定 API，不暴露内部指针和内存。
- 脚本崩溃不影响引擎，VM 可重启。
- API 版本化管理，旧版本 API 保持兼容。

```
└─────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────────────────────────────────────┐
│                    治理层                                  │
│  能力注册表 · 依赖图 · 影响分析 · 权限分类 · CI Gate        │
└─────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────────────────────────────────────┐
│                    通信层                                  │

                          │

                          │

```

## 小团队落地优先级

| 优先级 | 动作 | 理由 |
|--------|------|------|
| P0 | 选定 IDL，建立契约文件 | 没有契约，AI 生成代码无法审查 |
| P0 | 实现进程内事件总线 | 通信路径收敛是解耦的基础 |
| P0 | 建立 CI 架构测试 | 自动化 gate 替代人工审查 |
| P1 | 模块独立编译 + 热重载 | 开发效率和故障隔离的核心 |
| P1 | 能力注册表 | 防止 AI 重复生成功能重叠代码 |
| P1 | 权限分层 + 影响分析 | 让 AI 自主提交安全可控 |
| P2 | 命令缓冲 | 消除时序耦合，支持回放调试 |
| P2 | 沙箱 VM | 第三方扩展隔离 |
| P3 | Spec 驱动代码生成 | 最高级形态，需要前面基础 |

---

## 一句话总结

**原理是契约主权、数据所有权、通信收敛、权限分层、Spec 真相、故障隔离；要点是每个原理对应的架构约束；具体事项是团队要搭建的 IDL、事件总线、注册表、CI gate、热重载和沙箱。** 小团队从 P0 开始，逐步推进，最终让 AI 的生成速度转化为团队生产力，而不是维护负债。
