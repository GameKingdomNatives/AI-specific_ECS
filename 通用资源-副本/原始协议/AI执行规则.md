## 启动流程

每次开始工作时，按顺序读取：

1. **当前状态文档** → 知道现在在哪
2. **项目身份文档** → 知道方向
3. **边界约束文档** → 知道边界
4. **灵感池索引** → 知道有哪些可做的事
5. **上次迭代记录** → 知道上次做了什么、有什么遗留

读完这五份文档后，应有足够上下文开始迭代。

> 读取顺序有讲究：先事实（状态）再方向（身份）再约束（边界），避免先入为主。

## 执行原则

### 1. 方向优于步骤

收到迭代指令时，先确认方向是否与项目身份一致：

- ✅ "增强敌人威胁感" → 符合"互杀节奏"支柱
- ❌ "加一个护盾系统让玩家更耐打" → 违背"玻璃大炮"身份

方向不明确时，先问人。方向明确但步骤不清时，自己决定。

### 2. 边界硬性检查

每个检查点执行前，快速过一遍边界约束：

- 这个改动会让项目变成反模式吗？
- 会违反技术红线吗？
- 会打破调性约束吗？
- 在禁止操作清单里吗？

任何一项命中 → 停止，换方案或上报人。

### 3. 事实驱动

- 当前状态文档是最高事实来源。灵感池里的条目与当前状态矛盾时，以当前状态为准
- 不确定的代码行为 → 跑一下看，别猜
- 不确定的设计决策 → 做原型测，别想

### 4. 最小改动

每次检查点只做一件事，改最少的代码达到目标。能用一个组件解决的不建一个系统，能调参数的不改结构。

### 5. 即时记录

- 每个检查点完成后立即更新迭代记录
- 每个功能完成后立即更新当前状态文档中对应条目
- 发现新约束时立即追加到边界约束文档
- git commit message写清做了什么

### 6. 引擎优先理解

使用引擎能力进行开发前，必须先阅读引擎文档或源码中对应模块的内容，确认：

- 引擎提供了哪些内置能力（API、组件、系统、工具类）
- 这些能力的运行逻辑和生命周期是什么
- 有什么限制或约束（性能、内存、平台适配）

**不凭通用知识或假设使用引擎API**。引擎的架构决策（如ECS范式、组件纯数据、系统纯逻辑）和已有工具类（如`timeManager`、`AudioPlayer`、`randomInt()`）必须先确认再使用，避免重复造轮子或写出与引擎范式冲突的代码。

### 7. 灵感对齐

灵感池评审时必须对照项目身份文档：
- 灵感是否符合核心循环？不符合→拒绝或延后
- 灵感是否强化感觉词？不相关→降级
- 灵感是否与设计支柱冲突？冲突→看支柱优先级取舍

## 判断框架

### 如何判断一个灵感是否值得做

```
1. 符合项目身份？ → 否 → 拒绝/延后
2. 不违反边界约束？ → 违反 → 拒绝
3. 能提升核心循环体验？ → 不确定 → 先做小原型验证
4. 实现成本可控？ → 太大 → 拆成多个功能/迭代
5. → 采纳，纳入本轮迭代
```

### 如何判断当前最该做什么

```
1. 有P0级别的已知问题？ → 先修
2. 核心循环还没跑通？ → 优先让循环跑起来
3. 核心循环已跑通但体验差？ → 优先改善循环中最薄弱的环节
4. 核心循环体验还行？ → 从灵感池挑高优先级条目
```

### 如何判断是否需要方向校正

```
1. 迭代中发现了与项目身份根本矛盾的东西 → 需要校正身份
2. 发现边界约束阻碍了好的探索方向 → 需要校正边界
3. 连续3次迭代都没让体验变好 → 可能方向有问题，上报人
4. 迭代正常推进，体验持续改善 → 不需要校正
```

### 方向校正后灵感池如何处理

方向校正可能导致部分灵感池条目失效：

```
1. 身份变更 → 所有灵感重新过一遍对齐检查
2. 边界新增 → 标记违反新边界的条目为"已拒绝"，注明原因
3. 仅状态更新 → 不影响灵感池，继续迭代
```

## 禁止行为

1. ❌ 不读当前状态文档就开始写代码
2. ❌ 不读引擎文档/源码就使用引擎API进行开发
3. ❌ 不检查边界约束就执行改动
4. ❌ 一次迭代做超过2个灵感
5. ❌ 改动超出当前检查点范围（"顺手改"）
6. ❌ 自行修改项目身份文档
7. ❌ 自行删除边界约束
8. ❌ 跳过git commit直接开始下一个迭代
9. ❌ 把"计划做什么"写进当前状态文档（那是灵感池的事）
10. ❌ 功能完成后不更新当前状态文档（等迭代结束才一起更新会遗漏）
11. ❌ 方向校正后不检查灵感池中受影响的条目

## 与执行协议的分工边界

| 场景 | 本文件（规则） | 执行协议（SOP） |
|------|---------------|-----------------|
| 启动迭代 | 定义读什么文档 | 定义启动的具体步骤和产出 |
| 灵感池评审 | 定义对齐判断标准 | 定义评审的流程和决策步骤 |
| 执行检查点 | 定义边界检查和最小改动原则 | 定义检查点的执行顺序和验收方式 |
| 功能完成 | 定义"即时更新状态" | 定义更新哪些字段、怎么写 |
| 迭代完成 | 定义输出格式 | 定义commit/tag/归档的具体操作 |
| 方向校正 | 定义校正的判断标准 | 定义校正的分步操作流程 |

**原则**：规则说"应该怎样"，协议说"怎么做"。遇到冲突，规则优先。
