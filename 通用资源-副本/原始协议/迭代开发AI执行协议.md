# 迭代开发AI执行协议 v2.1

## 协议入口

当收到"启动迭代开发"或类似指令时，执行本协议。

**前置条件**：
- 项目身份文档已填写
- 当前状态文档已创建
- 边界约束文档已填写
- 灵感池已初始化
- Git仓库已初始化

**配套文档**：本协议定义执行SOP（步骤和时机），《AI执行规则》定义行为准则（判断标准和禁止行为）。执行时同时遵守两份文档，规则优先。

## 第一部分：迭代启动

### 步骤1：确认当前状态

按《AI执行规则-启动流程》读取五份项目文档：

1. 当前状态文档 → 了解实际进度
2. 项目身份文档 → 确认核心方向和感觉
3. 边界约束文档 → 确认红线
4. 灵感池索引 → 了解待办点子
5. 上次迭代记录 → 了解上次遗留

确认当前项目代码状态（`git status`）。

**输出**：当前状态简要说明

### 步骤2：灵感池评审（配合人完成）

1. 读取灵感池索引中所有"待评审"和"已采纳"条目
2. 按优先级（P0 > P1 > P2 > P3）排序
3. 按《AI执行规则-灵感对齐》检查每个条目是否与项目身份一致
4. 向人展示候选列表，由人挑选本次迭代要做的条目
5. 人不在或暂不决策时，优先挑选P0/P1且工作量小的条目

**原则**：
- 每次迭代挑选 1-2 个灵感池条目
- 不符合项目身份的条目直接标注并说明原因
- 不违反边界约束
- 不贪多

### 步骤3：确定迭代目标

1. 结合项目身份的方向 + 灵感池挑选的条目
2. 明确本次迭代的核心目标（1句话）
3. 按灵感→功能→检查点三级结构拆分
4. 明确验收标准
5. 明确文件范围
6. 按《AI执行规则-边界硬性检查》确认不违反约束

**输出**：迭代记录文件的基本信息部分

### 步骤4：创建迭代记录文件

1. 复制迭代模板
2. 填写基本信息、目标、范围、检查点
3. 保存到 `迭代开发/迭代记录/` 目录
4. 文件名格式：`迭代{编号}.md`
5. 在迭代记录索引中添加一行

## 第二部分：迭代执行

### 步骤5：按三级结构推进

将本次迭代按"灵感→功能→检查点"执行：

```
灵感1 → 功能1-1 → [检查点1-1-1, 1-1-2, ...] → 功能1-2 → [检查点1-2-1, ...]
灵感2 → 功能2-1 → [检查点2-1-1, 2-1-2, ...] → 功能2-2 → [检查点2-2-1, ...]
```

**每个检查点的执行循环**：

1. 执行前：按《AI执行规则-边界硬性检查》过一遍约束
2. 执行：单点串行，一次只做一个检查点
3. 执行后：记录结果，检查是否通过

**粒度要求**：
- 每个检查点应在 30分钟-2小时 内能完成
- 每个灵感拆2-5个功能，每个功能拆2-4个检查点
- 功能太大的话拆成多个功能或降级到下一个迭代

### 步骤6：记录执行过程

在迭代记录文件中实时记录：
- 当前灵感、当前功能、当前检查点的进度
- 做了什么、遇到了什么问题、怎么解决的
- 做了什么决策

**记录频率**：至少每个检查点完成后记录一次

### 步骤7：功能完成后的即时更新

每个功能（非检查点，是功能）完成后：

1. 更新当前状态文档中对应的已实现功能条目
2. 如果发现了新的架构决策，追加到当前状态文档
3. 如果发现了新的约束，追加到边界约束文档
4. 可选：git commit（建议功能级commit，粒度适中）

> ⚠️ 不要等到迭代结束才一起更新状态文档。功能完成后立即更新，避免遗漏。

### 步骤8：迭代自检验收

所有检查点完成后：

1. 对照验收标准逐一检查
2. 测试功能是否正常运行
3. 检查是否引入了新的bug
4. 检查是否有超出文件范围的修改
5. 按《AI执行规则-边界硬性检查》确认未违反约束
6. 对照项目身份文档，验证体验是否符合感觉词
7. 填写迭代记录中的边界校验和验收部分

**自检通过标准**：
- 所有验收项都达成
- 没有明显的bug
- 没有越权修改
- 没有违反边界约束
- 代码可以正常运行

1. 将已实现的条目状态改为"已实现"

### 步骤11：补全迭代记录

补全迭代记录中的所有部分：
- 执行过程记录
- 验收结论
- 回顾（做对/做错/改进）
- 下一次迭代方向建议

## 第四部分：日常操作规范

### 灵感池条目添加

当有新想法时：

1. 复制IDEA-模板.md，改编号为下一个可用编号
2. 按格式填写
3. 按《AI执行规则-灵感对齐》初步检查与项目身份的一致性
4. 标记状态为"待评审"
5. 在灵感池索引中添加一行
6. 不自行决定采纳还是拒绝，等评审

### 文件范围控制

- 严格按迭代记录中"范围"操作
- 超出范围的修改必须先上报人
- 不因"顺手"就改范围外的东西
- 执行前按《AI执行规则》检查边界约束，越线即停

### Git提交粒度

```
检查点级commit  — 可选，适合重要的检查点完成时
功能级commit    — 建议，粒度适中，方便回滚
迭代级commit    — 必须，迭代完成后的收尾commit
```

## 第五部分：方向校正流程

### 步骤14：方向校正评估（配合人完成）

1. 分析校正会影响哪些文档（项目身份/边界约束/当前状态）
2. 分析校正会影响哪些代码/系统
3. 按《AI执行规则-方向校正后灵感池如何处理》评估灵感池影响
4. 评估已完成工作的影响
5. 向人展示评估结果，由人最终决策

### 步骤15：生成方向校正记录

1. 复制校正模板
2. 填写校正基本信息、原因、范围分析、新旧对比、代价评估
3. 保存到 `迭代开发/方向校正记录/` 目录
4. 文件名格式：`校正{编号}.md`

### 步骤16：更新项目文档

1. 身份校正 → 修改项目身份文档，更新身份变更记录
2. 边界校正 → 修改边界约束文档，更新边界变更记录
3. 灵感池清理 → 标记受影响的条目（违反新边界的→拒绝，与身份不再对齐的→降级或拒绝）
4. 更新当前状态文档

### 步骤17：Git标记

```bash
git add .
git commit -m "[reset] 方向校正: 简述原因"
git tag pivot/YYYY-MM-DD -m "方向校正: 简述"
```

### 步骤18：校正完成，继续迭代

按更新后的文档继续迭代开发流程。

## 禁止行为

1. ❌ 一次迭代塞太多任务
2. ❌ 自行决定方向校正，必须上报人
3. ❌ 跳过验收流程
4. ❌ 超出文件范围操作
5. ❌ 不记录就做事
6. ❌ 功能完成后不更新当前状态文档
7. ❌ 迭代完成后不git commit
8. ❌ 方向校正后不处理灵感池中受影响的条目
