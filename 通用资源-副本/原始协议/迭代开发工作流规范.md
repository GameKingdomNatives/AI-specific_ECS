# 迭代开发工作流规范 v2.1

## 核心背景

游戏开发本质上是迭代式的——开发者在实际开发过程中会不断发现新的可能性、产生新的点子、调整方向。如果死守最初的规划，会导致好点子被压抑、计划与现实脱节。

本规范是迭代开发的**流程定义层**，与方向层/事实层/护栏层配合使用：
- **项目身份文档**定义方向（这项目是谁）
- **当前状态文档**记录事实（做到哪了）
- **边界约束文档**划定红线（不能变成什么）
- **迭代开发**是日常推进方式（灵感→原型→测试→反馈→再迭代）

---

## 核心概念

### 迭代（Iteration）
- 开发的基本执行单元，**小步快跑**式推进
- 每个迭代围绕1-2个灵感展开
- 迭代完成后必须验收，由人决定是否"完成"
- 迭代不对应固定阶段，按实际需要推进

### 灵感池（Idea Pool）
- 所有新想法、新功能、优化项的收容池
- 点子按优先级分级（P0/P1/P2/P3）
- 评审时必须对照项目身份文档对齐
- 每个迭代开始前从灵感池中挑选1-2个纳入本次迭代

### 方向校正（Direction Correction）
- 当迭代中发现需要重大调整时触发的机制
- 校正身份/边界/状态中与实际不符的部分
- 校正后必须检查灵感池中受影响的条目
- 一切以迭代得到的具体信息为最高依据
- 必须留下完整的决策记录

## 迭代开发完整流程

### 总体节奏

```
启动迭代 → 灵感池评审 → 确定迭代目标 → 执行迭代 → 迭代验收 → 记录结果
    ↑                                                          ↓
    └──────────────────── 方向校正判定 ────────────────────┘
```

### 详细步骤

#### 1. 迭代启动
- **触发方式**：上一个迭代验收通过后自动启动下一个
- **第一个迭代**：项目初始化完成后，由人手动启动
- **启动标志**：创建当次迭代记录文件

#### 2. 灵感池评审
- 从灵感池中挑选本次迭代要做的事情
- 优先挑选高优先级（P0/P1）的条目
- **必须对照项目身份文档检查对齐**：灵感是否符合核心循环、是否强化感觉词、是否与设计支柱冲突
- 每次迭代挑选 **1-2个** 灵感池条目
- 不符合项目身份的条目标注原因，不纳入
- 挑选结果记录在迭代记录中

#### 3. 确定迭代目标
- 结合项目身份的方向 + 灵感池挑选的条目
- 明确本次迭代的**核心目标**（1句话能说清）
- 明确**验收标准**（怎么算做完了）
- 明确**涉及的系统/文件范围**
- 边界硬性检查：确认不违反约束

#### 4. 执行迭代
- 按"灵感→功能→检查点"的三级结构推进：
  - **灵感**：本次迭代纳入的灵感池条目（1-2个）
  - **功能**：将每个灵感拆解为具体的功能点（每个灵感2-5个功能）
  - **检查点**：将每个功能拆解为可验证的检查点（每个功能2-4个检查点）
- 单点串行，一次只做一个检查点
- 3轮修复上限，超了就上报
- 每个功能完成后即时更新当前状态文档
- 每个检查点执行前做边界检查

#### 5. 迭代验收
- **由人最终决定**迭代是否完成
- 验收维度：
  - 核心目标是否达成
  - 灵感池条目是否按预期实现
  - 是否引入了新的问题
  - 是否违反边界约束
  - 整体体验是否变好（对照项目身份的感觉词）
- 不通过 → 继续修复或调整目标
- 通过 → 进入下一步

#### 6. 方向校正判定
- 检查本次迭代的结果是否触发**方向校正**
- 如果需要校正，执行方向校正流程（含灵感池清理）
- 如果不需要，正常推进

#### 7. 记录与归档
- 填写完整的迭代记录
- 更新灵感池中相关条目的状态
- 如果触发了方向校正，生成方向校正记录
- 确认当前状态文档已更新（功能级即时更新 + 迭代级最终确认）
- git commit + 打tag

## 灵感池分级与评审规则

### 分级标准

| 级别 | 名称 | 定义 | 处理优先级 |
|------|------|------|-----------|
| P0 | 必做 | 不做游戏就不成立的核心机制，或严重影响体验的问题 | 最高，必须尽快安排 |
| P1 | 重要 | 能显著提升游戏体验或开发效率的加分项 | 高，优先安排进迭代 |
| P2 | 可选 | 有空再说的小彩蛋、小优化 | 中，有空再做 |
| P3 | 存疑 | 听起来不错但不确定好不好玩，需要做原型验证 | 低，可先做小型验证 |

### 灵感对齐检查（必须）

每个灵感纳入迭代前，必须通过以下检查：

1. **核心循环对齐**：这个灵感是否服务于核心循环？
2. **感觉词增强**：这个灵感是否强化了至少一个感觉词？
3. **设计支柱冲突**：这个灵感是否与某个设计支柱冲突？冲突→按支柱优先级取舍
4. **边界约束合规**：这个灵感是否违反边界约束？违反即拒绝

不通过第1-2项 → 延后或拒绝
不通过第3项 → 评估取舍后决定
不通过第4项 → 直接拒绝

## 方向校正机制

### 触发条件

1. **核心玩法不达预期**：迭代后发现核心玩法体验不好，需要根本性调整
2. **与项目身份矛盾**：迭代中发现实际体验与身份文档定义的感觉词不符
3. **边界约束被触碰**：发现现有边界不合理，或发现需要新增边界
4. **重大新设定**：想到了绝妙的新设定或新方向，值得调整身份或边界

**判断原则**：如果这个变化会影响项目的核心身份或需要修改边界约束，就值得校正。

### 校正范围

- **身份校正**：核心循环/感觉词/钩子/支柱需要修改（极罕见，慎重）
- **边界校正**：需要增加/删除边界约束（偶尔发生，约束只增不减，删除需充分理由）
- **状态校正**：当前状态文档与实际不符，需要更新（常见，每次迭代后都应检查）
- **灵感池校正**：方向变更后，部分条目可能失效需要清理

### 灵感池清理规则

方向校正后必须检查灵感池：
- **身份变更** → 所有灵感重新过一遍对齐检查，不再对齐的标记"已拒绝"并注明原因
- **边界新增** → 违反新边界的条目标记"已拒绝"，注明违反哪条新约束
- **仅状态更新** → 不影响灵感池，继续迭代

### 操作流程

1. 判定：确认需要方向校正
2. 评估影响：分析校正会影响哪些文档和代码
3. 灵感池清理：按上述规则标记受影响的灵感条目
4. 修改对应文档：更新项目身份、边界约束或当前状态
5. 记录决策：填写方向校正记录
6. Git标记：commit + 打 `pivot/日期` tag
7. 继续迭代：按校正后的文档继续

## 核心原则

1. **小步快跑，避免迭代地狱**：每个迭代目标要小而明确，不要贪多
2. **身份对齐优先**：迭代方向必须与项目身份文档对齐，不然后面全是废工
3. **人的决策权**：迭代是否完成、是否触发方向校正，最终由人决定
4. **边界不可逾越**：边界约束是硬性红线，任何迭代都不能越线
5. **事实驱动**：当前状态文档记录事实，灵感池记录想法，两者不混
6. **即时更新**：功能完成后立即更新状态文档，不等迭代结束
