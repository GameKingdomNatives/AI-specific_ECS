# 一次可视化编辑器的评估记录：为什么我们不用 Onlook

这是一次**工具选型**的记录，不针对任何具体产品。结论先给：Onlook 能做的事有价值，但它的安装与维护成本超出我们愿意承担的范围，所以放弃。

## 1. 我们想要什么

一个可视化编辑界面的工具：能看真实组件、能拖拽调整、最好能把改动写回代码，并且**本地能用、不产生持续费用**。

## 2. 实际发生了什么

| 步骤 | 结果 |
|---|---|
| 安装运行时（Bun） | 成功 |
| 安装依赖 | 失败：某个包的安装脚本联网下载超时，进程直接退出 |
| 跳过安装脚本 | 可以绕过，但依赖是否完整无法确认 |
| 启动后端 | 失败：缺少 Supabase 命令行工具 |
| 安装该工具 | 新版可以全局安装；**旧版明确拒绝全局安装** |
| 改用旧版 | 安装时下载二进制失败（网络重置） |
| 手工下载二进制 | 成功（校验和一致） |
| 启动本地后端 | 失败：配置里声明了一个仓库中不存在的函数源码 |
| 禁用该函数 | 通过，开始执行数据库迁移 |
| 执行迁移 | 失败：迁移里直接删除对象存储的数据，被新版存储组件拒绝 |
| 想回退版本对齐 | 仍受上游配置与镜像版本约束，无法稳定复现 |

## 3. 代价拆解

| 代价 | 具体表现 |
|---|---|
| 环境成本 | 运行时 + 命令行工具 + 容器 + 数据库迁移，任一环节失败就全断 |
| 版本成本 | 命令行工具的版本决定它拉起的容器镜像版本，迁移能否执行取决于此 |
| 维护成本 | 每次升级都要重新对齐工具、镜像、迁移三套版本 |
| 人员成本 | 这些最终要由使用者承担，或由开发长期代管 |
| 交付风险 | 稳定发行物很少，能力是否覆盖本地项目未验证 |
| 收益不确定 | 换来的是「在真实组件上拖拽」；组件数量少时收益有限 |

## 4. 我们最终选了什么

- **Storybook**：本地运行、MIT 许可、离线可用；组件与状态即文档；可导出静态网页发给别人。
- **设计稿工具可选**：任何顺手的工具都行（含免费版 Figma），只用来画草图和标注；**不需要付费席位、不需要 Dev Mode、不需要云服务**。
- **代码是唯一事实源**：颜色/字号在 `tokens.ts`，组件在 `src/components/`，状态在 `*.stories.tsx`。

## 5. 什么情况下可以重新考虑

1. 它发布一个**能稳定打开本地项目**的版本，并有人实际验证成功；
2. 安装链能在目标系统上一次性复现（不依赖手工二进制与迁移补丁）；
3. 有明确的「必须所见即所得」需求，且愿意承担代码评审与门禁成本。

三条同时满足之前，不放进关键路径。

## 6. 一句话教训

**能本地复现的，不要外包给云；能零成本的，不要引入持续付费；工具是给人用的，先问使用者有什么。**
