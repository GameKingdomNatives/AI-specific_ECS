# 为什么不用 Onlook

这份 starter 不含 Onlook。不是「没试过」，而是试过之后主动排除。下面是完整代价与结论。

## 1. 我们想要什么

一个让设计方**能上手、本地可用、不产生持续费用**的 UI 工具，最好贴近 Figma 的操作习惯。Onlook 的方案是：在运行中的 React 组件画布上拖拽，并把改动写回 TypeScript 源码。

## 2. 实际发生了什么（时间线）

| 步骤 | 结果 |
|---|---|
| 安装 Bun | 成功（1.4.3） |
| `bun install` | 失败：`free-email-domains` 的 postinstall 联网超时，进程以 1 退出 |
| 绕过 postinstall | 成功，但依赖树未完整验证 |
| `bun backend:start` | 失败：`supabase` CLI 未安装 |
| 安装 Supabase CLI | 新版 2.121.0 可全局装；旧版 2.53.6 **拒绝全局安装** |
| 用仓库锁定的 2.53.6 | npm postinstall 下载二进制时 `ECONNRESET` |
| 改用手工二进制 | 成功（sha256 校验通过） |
| `supabase start` | 失败：`config.toml` 声明了仓库里不存在的 `stripe-webhook` 函数 |
| 禁用该函数 | 通过，开始跑迁移 |
| 迁移 0008 | 失败：直接 `delete from storage.objects` 被新版 Storage 拒绝（SQLSTATE 42501） |
| 版本回退对齐 | 仍受上游配置与镜像版本约束，不可控 |

## 3. 代价拆解

| 代价 | 具体表现 |
|---|---|
| 环境成本 | Bun + Supabase CLI + Docker + 数据库迁移，任一环节失败就全断 |
| 版本成本 | CLI 版本决定容器镜像版本；仓库锁的文件与迁移假设必须同时匹配 |
| 维护成本 | 每次升级都要重新对齐 CLI、镜像、迁移 |
| 人员成本 | 这些都要设计师承担或由开发长期代管 |
| 交付风险 | 稳定产物只有 2025-07 的桌面安装包；能否打开本地项目未验证 |
| 价值不确定 | 即使装成，收益是「在真实组件上拖拽」，而我们只有一条控制条 |

## 4. 我们最终选了什么

- **Storybook**：本地、MIT、离线；组件与状态即文档；静态包可发给设计。
- **Figma 免费版**：仅作草稿/标注，不接 Dev Mode（云端、付费、产物不能直接用）。
- **代码为唯一事实源**：token 在 `src/tokens.ts`，组件在 `src/components/`。

## 5. 什么情况下可以重新考虑 Onlook

1. 它发布一个**能打开本地项目**的稳定桌面版，且你实际验证成功；
2. 上游安装链能在 Windows 上一次性复现（不依赖手工二进制与迁移补丁）；
3. 有明确的「必须所见即所得」需求，且愿意承担 review 与门禁成本。

三条同时满足之前，不把它放进关键路径。

## 6. 教训一句话

**能本地复现的，不要外包给云；能零成本的，不要引入持续付费；工具是给人用的，先问使用者有什么。**
