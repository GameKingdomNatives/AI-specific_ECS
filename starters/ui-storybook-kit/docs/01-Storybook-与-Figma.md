# Storybook 与 Figma 各管什么

## 1. 一句话区别

- **Figma**：画「界面应该长什么样」，是设计稿工具，不产出可运行代码。
- **Storybook**：展示「组件实际长什么样」，是真实代码的状态目录，能被交付、被测试、被版本管理。

两者不是替代关系。设计稿可以继续用任何工具画；**验收以 Storybook 为准**。

## 2. 对比

| 维度 | Figma（或任何设计稿工具） | Storybook |
|---|---|---|
| 产物 | 设计文件 | 可运行的组件 + 静态网页 |
| 是否可运行 | 否（原型是模拟） | 是（真实渲染） |
| 是否进版本库 | 一般不进 | 进（`*.stories.tsx`） |
| 使用者要装什么 | 浏览器 | 浏览器（看静态包） |
| 费用 | 免费版通常够用；进阶功能可能收费 | MIT，免费商用 |
| 能改代码吗 | 不能 | 不能（它展示代码） |
| 适合做什么 | 探索布局、视觉、流程 | 固化状态、验收、交付、回归 |

## 3. 概念对应表（从设计稿翻译到 story）

| 设计稿里的东西 | Storybook 里的对应物 |
|---|---|
| 组件（Component） | `src/components/Xxx.tsx` |
| 组件变体（Variant） | 一个 story，或 `args`（如 `tone: 'primary'`） |
| 组件属性（Properties） | props + `argTypes`（Controls 面板） |
| 页面/画板（Frame） | 一个 story（或把几个组件组合起来的一个 story） |
| 颜色/字号/间距 | `src/tokens.ts` + Tailwind 类 |
| 交互原型（Prototype） | `play` 函数（需装测试插件）或人工评审 |
| 标注/切图 | story 本身（直接看实现） |
| 版本历史 | git 提交历史 |

## 4. 工作方式怎么变

**以前**：设计画完 → 开发照着写 → 设计发现不一致 → 再改。

**现在**：

1. 设计稿照常画，交付时写清「组件名 + 状态 + 期望值」；
2. 开发在 `src/components/` 实现，并给每个状态写一个 story；
3. 双方打开 Storybook（本地或静态包）对照；
4. 差异按「哪里、期望、为什么」提，开发改组件与 story；
5. 重新构建静态包，作为这一轮的验收物。

讨论对象从「一张图」变成「真实组件 + 明确状态」，不会出现「你看的是设计稿，我看的是实现」的错位。

## 5. 什么不能从设计稿直接搬

- **画布类内容**（地图、图表、游戏画面、视频）不是普通网页元素，Storybook 只覆盖 DOM 组件；
- 复杂拖拽/画布交互：能展示但不易模拟，需要另写交互测试；
- 像素级动画曲线：以代码为准，设计稿只给参考；
- 设计稿里的占位文案：story 里要换成真实结构的假数据，并显式给空状态/错误状态。

## 6. 成本对照

| 项 | 依赖云端设计工具的高级能力 | 本方案（Storybook） |
|---|---|---|
| 使用者费用 | 可能需要订阅 | 0 |
| 是否离线 | 否 | 是 |
| 产物能否直接用 | 否 | 是（静态网页 + 组件） |
| 持续依赖 | 账号与订阅 | 无 |

结论：**设计稿工具当草稿本，Storybook 当验收台。**
